АЛГОРИТМЫ ПРИЕМКИ, ОТГРУЗКИ И СИНХРОНИЗАЦИИ

ТЕРМИНЫ
Серверная БД — основная база данных на сервере

Локальная БД — кэш на ТСД (хранит коробки со статусами Draft, Active, Reserved)

Queue — очередь офлайн-транзакций (приемка/отгрузка)

ProblemBoxes — таблица на сервере для коробок с ошибками при синхронизации

LastModifiedTime — таблица на сервере с одним полем LastChanged

LastChanged — timestamp последнего изменения ЛЮБОЙ коробки на сервере

ServerLastModifiedTime — таблица из локальной БД с одним полем ServerLastChanged

ServerLastChanged — timestamp из локальной БД (копия LastChanged с сервера)

isPartial — ТОЛЬКО локальная переменная в ShippingViewModel (полная/частичная отгрузка)

Отмена сканирования — удаление коробки из списка отсканированных в текущей сессии
приёмки/отгрузки до подтверждения операции. Выполняется по кнопке ✕ рядом с коробкой.
Сопровождается откатом: удаление соответствующей pending-транзакции из Queue и
восстановление состояния локальной БД (через OfflineService.RevertTransaction).

Локация — место хранения коробок. Обозначается ШК локации. Все коробки, отсканированные
в сессии, привязываются к текущей локации.

0. ФОРМАТЫ ШТРИХКОДОВ

0.1. ШК ЛОКАЦИИ

Формат: X-XX-XX (например, A-01-01)

Ровно 2 разделителя "-" → 3 части.

Части могут содержать буквы и цифры.

Регистр НЕ важен: "A-01-01" и "a-01-01" — одна и та же локация.
При парсинге нормализуется в UPPER.

0.2. ШК КОРОБКИ

Формат: ean13-количество-сорт-номер_коробки (например, 2200000001511-100-9-31)

Ровно 3 разделителя "-" → 4 части.

Все части — ТОЛЬКО цифры. Если хотя бы одна часть содержит нецифровой символ — ШК невалиден.

ean13 — цифры.

количество — цифры, СТРОГО > 0.

сорт — цифры, СТРОГО из набора {1, 2, 3, 5, 9}:
  9 → Premium
  1 → First
  2 → Second
  3 → Decorated
  5 → Rejected

номер_коробки — цифры, СТРОГО > 0.

0.3. РАЗЛИЧЕНИЕ ФОРМАТОВ

Подсчёт разделителей "-":
  ровно 2 → ШК локации
  ровно 3 → ШК коробки
  иначе → НЕВАЛИДНЫЙ ШК

Если ШК не подходит ни под локацию, ни под коробку:
  → SetError("Некорректный формат штрихкода")
  → транзакция в Queue НЕ создаётся
  → коробка НЕ добавляется в сессию
  → локальная БД НЕ трогается

ПРАВИЛА
Локальная БД хранит ВСЕ коробки со статусами Draft, Active, Reserved

Флаг isPartial НЕ ХРАНИТСЯ в БД (ни серверной, ни локальной)

isPartial используется ТОЛЬКО в UI для переключения режимов отгрузки

При приемке: если коробки нет на сервере — ПРИНУДИТЕЛЬНАЯ ПРИЕМКА

При отгрузке: количество берется ТОЛЬКО из локальной БД

Локация может быть отсканирована В ЛЮБОЙ МОМЕНТ сессии приёмки.
Все коробки в текущей сессии (уже отсканированные и будущие) привязываются
к ПОСЛЕДНЕЙ отсканированной локации. Если локация отсканирована повторно —
ничего не меняется.

Если локация не найдена в локальной БД — вместо ошибки ставим "UNKNOWN".
Синхронизация локаций при этом НЕ запускается (только в общем SyncManual).

Отмена сканирования доступна для любой коробки в списке отсканированных в текущей
сессии (и в приёмке, и в отгрузке). Диалог подтверждения НЕ показывается.

Отмена сканирования выполняется ТОЛЬКО до подтверждения операции. После подтверждения
(ConfirmOperation) список очищается, отменять нечего.

Отмена сканирования НЕ трогает сервер. Все действия — только локальные: откат
pending-транзакции в Queue + восстановление boxes_cache.

Механизм отката — OfflineService.RevertTransaction. Для Receiving:
- если коробка создавалась локально (wasCreatedLocally = true) → удалить из boxes_cache;
- если коробка уже существовала (wasCreatedLocally = false) → вернуть previousStatus.

Для Shipping: восстановить previousStatus и previousQuantity в boxes_cache;
если запись была удалена (стала архивной) — пересоздать её из payload.

Если pending-транзакция по barcode не найдена (маловероятный сценарий: транзакция
уже синхронизирована или потеряна) — коробка удаляется только из UI, локальная БД
не трогается. При следующей синхронизации сервер вернёт актуальное состояние.

Фоновое обновление локальной БД ОТСУТСТВУЕТ

Проверка LastChanged выполняется ТОЛЬКО:

после логина

во время синхронизации

Синхронизация РУЧНАЯ (кроме автоматической после логина). Оператор сам решает, когда запускать.

retry_count и MAX_RETRY_COUNT НЕ ИСПОЛЬЗУЮТСЯ. При ручной синхронизации нет «долбёжки» сервера — каждая попытка инициирована человеком.

Классификация ошибок синхронизации:

Сценарий 1 (нет связи) — SyncBoxes вернул null. Транзакции НЕ трогаем. Показываем оператору сообщение «Сервер недоступен».

Сценарий 2 (сервер лежит / 5xx) — SyncBoxes вернул null. Транзакции НЕ трогаем. Показываем оператору сообщение «Сервер недоступен».

Сценарий 3 (бизнес-ошибка) — сервер ответил. Тогда:

Success == true → удаляем транзакцию

ProblemBoxCreated == true → сервер сам создал ProblemBox, удаляем транзакцию

иначе → транзакцию НЕ трогаем (оператор повторит синхронизацию вручную)

1. СИНХРОНИЗАЦИЯ ПОСЛЕ ЛОГИНА
Выполнить пункт 4 (СИНХРОНИЗАЦИЯ) сразу после логина.

2. ПРИЕМКА
2.1. Сканирование штрихкода
2.2. Определение типа ШК (см. п. 0.3):
  ШК локации → п. 2.3
  ШК коробки → п. 2.4
  Невалидный → SetError("Некорректный формат штрихкода"), конец.

2.3. Обработка ШК локации:
  2.3.1. Нормализовать в UPPER.
  2.3.2. Найти локацию в локальной БД по code.
  2.3.3. Если не найдена → CurrentLocation = "UNKNOWN".
       Синхронизацию локаций НЕ запускать.
  2.3.4. Если найдена и неактивна → предупреждение, CurrentLocation не менять.
  2.3.5. Если найдена и активна → CurrentLocation = <code>.
  2.3.6. Всем коробкам в ScannedBoxes проставить LocationCode = CurrentLocation.
  2.3.7. LastScannedBarcode = <code>. Показать статус "Локация: ...". Конец.

2.4. Обработка ШК коробки:
  2.4.1. Проверка дублирования в сессии.
  2.4.2. TryParseBoxBarcode — если невалиден → SetError("Некорректный формат штрихкода"), конец.
  2.4.3. Проверка наличия в локальной БД:
    2.4.3.1. Нет → создать коробку со статусом Active.
    2.4.3.2. Есть → проверить статус:
      Draft → изменить на Active
      Active → ❌ ошибка "Коробка уже активна"
      Reserved → ❌ ошибка "Коробка зарезервирована"
      Shipped → ❌ ошибка "Коробка отгружена"
      Empty → ❌ ошибка "Коробка пуста"
      Discarded → ❌ ошибка "Коробка списана"
  2.4.4. Сохранить в локальную БД:
    status = Active
    location_code = CurrentLocation
    created_at = <время сканирования на ТСД>
  2.4.5. Добавить в сессию.
  2.4.6. Создать транзакцию в Queue (тип: Receiving)
    created_at = <время сканирования>
  2.4.7. При подтверждении → синхронизация (п.4).

2.5. Отмена сканирования (кнопка ✕ рядом с коробкой в списке):
  2.5.1. Найти pending-транзакцию в Queue по barcode коробки.
  2.5.2. Если найдена → OfflineService.RevertTransaction:
    - wasCreatedLocally = true → удалить коробку из boxes_cache;
    - wasCreatedLocally = false → вернуть previousStatus в boxes_cache.
    Удалить транзакцию из Queue.
  2.5.3. Если не найдена → удалить только из UI (см. ПРАВИЛА).
  2.5.4. Убрать коробку из ScannedBoxes, пересчитать ScannedCount.
  2.5.5. Если список пуст → ClearSession.
  2.5.6. Диалог подтверждения НЕ показывается.

3. ОТГРУЗКА
3.1. Сканирование штрихкода
3.2. Определение типа ШК (см. п. 0.3):
  ШК локации → игнорировать (в отгрузке локация не нужна).
  ШК коробки → п. 3.3.
  Невалидный → SetError("Некорректный формат штрихкода"), конец.

3.3. Проверка наличия в локальной БД:

3.3.1. Нет → ❌ ошибка "Коробка не найдена"

3.3.2. Есть → проверить статус:
Active → ✅ продолжить
Draft → ❌ ошибка "Коробка не активирована"
Reserved → ✅ продолжить (с предупреждением)
Shipped → ❌ ошибка "Коробка уже отгружена"
Empty → ❌ ошибка "Коробка пуста"
Discarded → ❌ ошибка "Коробка списана"
3.4. Количество из локальной БД (current_quantity)
3.5. Выбор типа отгрузки (isPartial в ViewModel):

3.5.1. Полная → списать всё

3.5.2. Частичная → ввод количества (проверка <= current_quantity)
3.6. Рассчитать новый статус:

3.6.1. Полная отгрузка → Shipped (кол-во = 0)

3.6.2. Частичная, new_quantity == 0 → Empty

3.6.3. Частичная, new_quantity > 0 → Active
3.7. Сохранить в локальную БД
status = <Shipped | Empty | Active>
current_quantity = <new_quantity>
updated_at = <время сканирования>
3.8. Добавить в сессию
3.9. Создать транзакцию в Queue (тип: Shipping)
3.10. При подтверждении → синхронизация (п.4)
3.11. Отмена сканирования (кнопка ✕ рядом с коробкой в списке):
  3.11.1. Найти pending-транзакцию в Queue по barcode коробки.
  3.11.2. Если найдена → OfflineService.RevertTransaction:
    - восстановить previousStatus и previousQuantity в boxes_cache;
    - если запись была удалена (стала архивной) → пересоздать из payload.
    Удалить транзакцию из Queue.
  3.11.3. Если не найдена → удалить только из UI (см. ПРАВИЛА).
  3.11.4. Убрать коробку из ScannedBoxes, пересчитать ScannedCount.
  3.11.5. Если список пуст → ClearSession, сбросить _currentSelectedBox,
         CanPartialShip = false, ShipQuantity = 0.
  3.11.6. Если осталась одна → _currentSelectedBox = первая, MaxQuantity =
         current_quantity, UpdateModes.
  3.11.7. Если осталось больше одной → CanPartialShip = false, IsFullShipmentMode = true,
         IsPartialShipmentMode = false, ShipQuantity = сумма current_quantity.
  3.11.8. Диалог подтверждения НЕ показывается.

4. СИНХРОНИЗАЦИЯ
4.1. Подготовка
Получить все несинхронизированные транзакции (is_synced = 0)

Разделить:

Группа A: Receiving (сортировка по created_at ASC)

Группа B: Shipping (сортировка по created_at ASC)

4.2. Отправка на сервер
Собрать все транзакции в один запрос SyncBoxesRequest

Отправить на сервер /api/tsd/sync/boxes

4.3. Обработка ответа
4.3.1. Если response == null (нет связи / сервер лежит):

Транзакции НЕ трогаем

Бросаем InvalidOperationException с сообщением: «Сервер недоступен. Транзакции остались в очереди. Повторите синхронизацию позже.»

UI показывает DisplayAlert оператору

Конец синхронизации

4.3.2. Если сервер ответил, для каждой транзакции из response.ProcessedTransactions:

Если Success == true:

Удалить транзакцию из локальной очереди

Если ProblemBoxCreated == true:

Сервер сам создал ProblemBox

Удалить транзакцию из локальной очереди

Иначе:

Транзакция НЕ трогаем

Логируем ошибку

Оператор повторит синхронизацию вручную

4.3.3. Транзакции, которые сервер не упомянул в ответе:

НЕ трогаем

Логируем предупреждение

4.4. Обновить локальную БД
4.4.1. Получить LastChanged с сервера

4.4.2. Получить ServerLastChanged из локальной БД

4.4.3. Если LastChanged > ServerLastChanged:

4.4.3.1. Получить все коробки (Draft, Active, Reserved)

4.4.3.2. Получить pending-транзакции (barcode'ы с локальными изменениями)

4.4.3.3. Очистить boxes_cache, кроме barcode'ов с локальными изменениями

4.4.3.4. Записать загруженные коробки, кроме barcode'ов с локальными изменениями

4.4.3.5. Обновить ServerLastChanged = LastChanged

4.5. Готово
4.6. LastModifiedTime.LastChanged обновляется триггером БД

5. ТАБЛИЦА PROBLEM_BOXES (серверная)
Назначение: хранение коробок, которые не были приняты или отгружены во время синхронизации, т.е. коробки с ошибками.

Создаётся: сервером при обработке SyncBoxes.

Поля (рекомендуется):

id

barcode

box_id (nullable)

operation_type (Receiving / Shipping)

comment (текст ошибки)

created_at

6. ТАБЛИЦА LAST_MODIFIED_TIME (серверная)
Назначение: хранение timestamp (LastChanged) последнего изменения ЛЮБОЙ коробки на сервере.

7. ТАБЛИЦА SERVER_LAST_MODIFIED_TIME (локальная)
Назначение: хранение timestamp (ServerLastChanged) последнего изменения ЛЮБОЙ коробки на сервере.

8. СИНХРОНИЗАЦИЯ ОЧЕРЕДИ (ДЕТАЛИ)
8.1. Синхронизация запускается:

Вручную из SyncQueuePage или из HomePage при нажатии на кнопку «Синхр.»

Автоматически после логина (если есть транзакции)

8.2. Порядок:

Сначала ВСЕ приемки

Потом ВСЕ отгрузки

Обновление локальной БД с сервера

8.3. При ошибке:

Нет связи / сервер лежит → InvalidOperationException с человеческим текстом → DisplayAlert оператору. Транзакции НЕ трогаем.

Бизнес-ошибка (сервер ответил) → сервер сам создал ProblemBox → локальная транзакция удаляется.

Сервер ответил, но ProblemBox не создан → транзакция НЕ трогаем, оператор повторит синхронизацию вручную.

8.4. retry_count и MAX_RETRY_COUNT НЕ ИСПОЛЬЗУЮТСЯ. Синхронизация ручная — каждая попытка инициирована человеком.

8.5. Отмена сканирования и Queue:
Отмена сканирования удаляет pending-транзакцию из Queue до того, как оператор
запустит синхронизацию. Это ГАРАНТИРУЕТ, что отменённая коробка НЕ уйдёт на сервер.
Если по какой-то причине транзакция уже синхронизирована (маловероятно) — коробка
удаляется только из UI, а серверная БД остаётся без изменений. Рассинхрон
устранится при следующей синхронизации (п. 4.4 обновит boxes_cache с сервера).
