АЛГОРИТМЫ ПРИЕМКИ, ОТГРУЗКИ И СИНХРОНИЗАЦИИ
============================================

ТЕРМИНЫ:
- Серверная БД — основная база данных на сервере
- Локальная БД — кэш на ТСД (хранит коробки со статусами Draft, Active, Reserved)
- Queue — очередь офлайн-транзакций (приемка/отгрузка)
- ProblemBoxes — таблица на сервере для коробок с ошибками при синхронизации
- LastModifiedTime - таблица на сервере с одним полем LastChanged
- LastChanged — timestamp последнего изменения ЛЮБОЙ коробки на сервере
- ServerLastModifiedTime - таблица из локальной БД с одним полем ServerLastChanged
- ServerLastChanged — timestamp из локальной БД (копия LastChanged с сервера)
- isPartial — ТОЛЬКО локальная переменная в ShippingViewModel (полная/частичная отгрузка)

ПРАВИЛА:
1. Локальная БД хранит ВСЕ коробки со статусами Draft, Active, Reserved
2. Флаг isPartial НЕ ХРАНИТСЯ в БД (ни серверной, ни локальной)
3. isPartial используется ТОЛЬКО в UI для переключения режимов отгрузки
4. При приемке: если коробки нет на сервере — ПРИНУДИТЕЛЬНАЯ ПРИЕМКА
5. При отгрузке: количество берется ТОЛЬКО из локальной БД
6. Фоновое обновление локальной БД ОТСУТСТВУЕТ
7. Проверка LastChanged выполняется ТОЛЬКО:
   - после логина
   - во время синхронизации


1. СИНХРОНИЗАЦИЯ ПОСЛЕ ЛОГИНА
   ----------------------------------------
   Выполнить пунк 4 СИНХРОНИЗАЦИЯ сразу после логина.


2. ПРИЕМКА
   ---------
   2.1. Сканирование штрихкода
   2.2. Проверка дублирования в сессии
   2.3. Проверка наличия в локальной БД:
        2.3.1. Нет → создать коробку со статусом Active
        2.3.2. Есть → проверить статус:
              - Draft → изменить на Active
              - Active → ❌ ошибка "Коробка уже активна"
              - Reserved → ❌ ошибка "Коробка зарезервирована"
              - Shipped/Empty → ❌ ошибка "Коробка отгружена/пуста"
   2.4. Сохранить в локальную БД (status = Active)
   2.5. Добавить в сессию
   2.6. Создать транзакцию в Queue (тип: Receiving)
   2.7. При подтверждении → синхронизация (п.4)


3. ОТГРУЗКА
   ----------
   3.1. Сканирование штрихкода
   3.2. Проверка дублирования в сессии
   3.3. Проверка наличия в локальной БД:
        3.3.1. Нет → ❌ ошибка "Коробка не найдена"
        3.3.2. Есть → проверить статус:
              - Active → ✅ продолжить
              - Draft → ❌ ошибка "Коробка не активирована"
              - Reserved → ✅ продолжить (с предупреждением)
              - Shipped → ❌ ошибка "Коробка уже отгружена"
              - Empty → ❌ ошибка "Коробка пуста"
   3.4. Количество из локальной БД (current_quantity)
   3.5. Выбор типа отгрузки (isPartial в ViewModel):
        3.5.1. Полная → списать всё
        3.5.2. Частичная → ввод количества (проверка <= current_quantity)
   3.6. Рассчитать новый статус:
        3.6.1. new_quantity == 0 → Empty (2)
        3.6.2. new_quantity > 0 → Active (1)
        3.6.3. Если коробка была Reserved и isFullShipment → Shipped (3)
   3.7. Сохранить в локальную БД
   3.8. Добавить в сессию
   3.9. Создать транзакцию в Queue (тип: Shipping)
   3.10. При подтверждении → синхронизация (п.4)


4. СИНХРОНИЗАЦИЯ
   ---------------
   4.1. Получить все несинхронизированные транзакции (is_synced = 0)
   4.2. Разделить:
        - Группа A: Receiving (сортировка по created_at ASC)
        - Группа B: Shipping (сортировка по created_at ASC)
   
   4.3. ОБРАБОТАТЬ ГРУППУ A (ВСЕ ПРИЕМКИ):
        Для каждой транзакции:
            4.3.1. Получить barcode
            4.3.2. Запросить коробку на сервере
            4.3.3. Если коробки нет:
                  ПРИНУДИТЕЛЬНАЯ ПРИЕМКА
                  Создать коробку на сервере со статусом Active
                  В comment: "Коробка принята принудительно: не найдена на сервере"
                  Удалить транзакцию
            4.3.4. Если статус == Draft:
                  Активировать коробку (Draft → Active)
                  Удалить транзакцию
            4.3.5. Если статус != Draft:
                  Ошибка, коробку не принимать, оставить ез изменений.
                  Добавить запись в таблицу ProblemBoxes
		  В comment: Попытка приемки коробки: серверный статус {статус}"
                  Удалить транзакцию
   
   4.4. ОБРАБОТАТЬ ГРУППУ B (ВСЕ ОТГРУЗКИ):
        Для каждой транзакции:
            4.4.1. Получить boxId из payload
            4.4.2. Запросить коробку на сервере
            4.4.3. Если коробки нет → ❌ ошибка, retry_count++
            4.4.4. Если статус == Draft → ❌ ошибка, retry_count++ (не активирована)
            4.4.5. Если статус == Shipped || Empty → ❌ ошибка, retry_count++
            4.4.6. Если статус == Active || Reserved:
                    4.4.6.1. Если isFullShipment == true:
                              → /api/boxes/ship
                              → статус Shipped
                            Иначе:
                              → /api/boxes/consume (с quantity)
                              Если new_quantity == 0 → Empty
                              Иначе → Active
                    4.4.6.2. Если успех → удалить транзакцию
                    4.4.6.3. Если ошибка → retry_count++,
            4.4.7. Если статус == Discarded → ❌ ошибка, retry_count++
	    4.4.8. Если коробка был с ошибкой, то добавить запись в таблицу ProblemBoxes с комментарием
   
   4.5. ОБНОВИТЬ ЛОКАЛЬНУЮ БД:
     	4.5.1. Получить LastChanged с сервера
     	4.5.2. Получить ServerLastChanged из локальной БД
	     4.5.3. Если LastChanged > ServerLastChanged:
        	    4.5.3.1. Загрузить все коробки (Draft, Active, Reserved)
	            4.5.3.2. Очистить локальную boxes_cache
	            4.5.3.3. Записать загруженные коробки
        	    4.5.3.4. Обновить ServerLastChanged = LastChanged
   4.6. Готово


5. ТАБЛИЦА PROBLEM_BOXES (серверная)
   -----------------------------------
   Назначение: хранение коробок, которые не были приняты или отгружены во время синхронизации, т.е. коробки с ошибками

6. ТАБЛИЦА LAST_MODIFIED_TIME (серверная)
   -----------------------------------
   Назначение: хранение timestamp (LastChanged) последнего изменения ЛЮБОЙ коробки на сервере
   
7. ТАБЛИЦА SERVER_LAST_MODIFIED_TIME (локальная)
   -----------------------------------
   Назначение: хранение timestamp (ServerLastChanged) последнего изменения ЛЮБОЙ коробки на сервере


8. СИНХРОНИЗАЦИЯ ОЧЕРЕДИ (ДЕТАЛИ)
   --------------------------------
   8.1. Синхронизация запускается:
        - При подтверждении операций (приемка/отгрузка)
        - Вручную из SyncQueuePage
        - Автоматически после логина (если есть транзакции)
   
   8.2. Порядок:
        1. Сначала ВСЕ приемки
        2. Потом ВСЕ отгрузки
        3. Обновление локальной БД с сервера
   
   8.3. При ошибке:
        - error_message = текст ошибки
        - Транзакция остается в очереди
